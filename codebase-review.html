Minnow codebase and public API review

A consumer-focused review of the architecture, implementation quality, complexity, public API, onboarding, documented guarantees, and wire-format behavior of Minnow 0.1.0.

Review date: 19 July 2026 Scope: full workspace Status: open findings Resolved findings removed after verification

Executive assessment

The core idea is compelling, the source is generally well organized, and the test and CI discipline are unusually good for a 0.1 crate. The arithmetic coder and bit I/O are sensibly delegated to existing libraries, while the domain-specific type weighting and derive implementation are kept readable.

The current release is nevertheless not ready for ordinary downstream consumers. Valid float models can panic during valid decoding, and several prominent safety and optimality claims are broader than the implementation supports. These are fixable, but the float-domain bug should be treated as a release blocker.

1. Valid, non-grid-aligned float bounds can make valid decoding panic

FloatModel::new(0.0..=0.96, 1) is accepted because round((max - min) × 10) produces ten steps. Encoding 0.96 selects symbol ten; decoding symbol ten produces 1.0, outside the declared range. In debug builds, the arithmetic-coding wrapper subsequently reaches Minnow's in-range debug_assert and panics. With that assertion removed, the decoded value remains outside the configured domain.

Evidence: constructor step rounding in src/float.rs:52–87; scale/unscale in src/float.rs:146–162. Reproduced with a valid encode/decode round trip.

Recommended solution

Define the quantized domain explicitly as an integer index range and guarantee that every index maps inside min..=max. A robust design is:

  1. Compute the step size once and validate that it is finite and nonzero.
  2. Use a well-defined endpoint policy—preferably reject bounds that are not aligned to the declared decimal grid, because this keeps the schema honest and makes both endpoints predictable.
  3. Store the validated denominator or maximum index in the model rather than recomputing it through floating-point operations.
  4. Ensure unscale(i) is within the configured range for every valid i.

Promising alternatives

  • Permit unaligned bounds but use floor for the final index and document that the effective maximum is the last grid point at or below max. Encoding must then reject or deliberately project values above that effective maximum.
  • Keep rounding but clamp the decoded endpoint back to max. This avoids the panic, but creates a nonuniform final bucket and invalidates the simple uniform-cardinality model unless its probability width is adjusted.
  • Represent decimal bounds and precision with scaled integers or a decimal crate. This is the most predictable wire model, at the cost of a broader API change.

Acceptance criteria

  • Every configuration accepted by FloatModel::new round-trips every valid symbol without panic.
  • Every decoded value is finite and lies inside the advertised inclusive range.
  • Property tests cover unaligned positive and negative bounds, negative precision, narrow ranges, and values within half a step of both endpoints.
  • Macro-time validation and runtime validation share the same implementation or shared specification.
High

2. Bounded-sequence truncations routinely decode as successful wrong values

The pre-decode length check accepts any byte count between the cheapest and most expensive value. That interval is necessarily broad for Vec and String. The arithmetic decoder then treats exhausted input as zero padding.

For Vec<bool> with max_len = 64, a 64-element value encoded to nine bytes. Every truncation from one through eight bytes decoded as Ok with incorrect contents. This contradicts the early README statement that truncated or malformed bytes are always errors, and the method documentation that says the check catches truncation.

Evidence: length-window logic in src/encodeable_custom.rs:137–155; broad sequence best/worst cases in src/seq.rs:144–151; contradictory claims in README.md:51 and 289–299.

Recommended solution

Treat integrity and truncation detection as explicit framing responsibilities. Add a small, first-class framed API that includes payload length and an integrity value:

  • encode_framed writes a schema/version identifier, encoded payload length, payload, and optional CRC or MAC.
  • decode_framed verifies the exact payload length and integrity before arithmetic decoding.
  • Keep encode_bytes/decode_bytes as raw expert APIs, but rename or document them prominently as non-validating.

At minimum, remove every unconditional claim that raw decoding detects truncation.

Promising alternatives

  • Decode, re-encode canonically, and compare the bytes. This may catch truncation without a checksum, but it requires proving canonical uniqueness and adds full re-encoding cost.
  • Expose an API that accepts an independently trusted exact bit or byte length from the transport. This fits protocols that already provide framing.
  • Add an end-of-message sentinel model. It can improve truncation detection, but without an integrity code some corrupt streams will still decode to a valid sentinel.

Acceptance criteria

  • Documentation distinguishes raw arithmetic decoding from integrity-checked framing before the quick start.
  • Tests truncate every byte of fixed and variable-length values and assert behavior promised by the selected API.
  • If a framed API is added, every proper truncation fails deterministically.

3. Saturating u128 weights invalidate automatic minimax weighting

Payload cardinalities saturate beyond roughly sixteen bytes. Derived enums then pass the saturated sentinel through .get() as a real discriminant weight, destroying relative cardinality. For an enum containing [u8; 16] and [u8; 32] variants, both weights saturate identically, so each gets a one-bit discriminant. The observed variants encoded to 17 and 33 bytes rather than equal lengths.

Evidence: saturation documented in src/weight.rs:34–43; saturated values used in generated discriminants at minnow-derive/src/write.rs:383–389; headline equality claim at README.md:97–107.

Recommended solution

Use exact arbitrary-precision cardinalities for schema construction, then rescale them once when building the bounded arithmetic model. num-bigint::BigUint is the straightforward solved solution: products and sums remain exact, relative interval widths can be calculated correctly, and the final widths can still be normalized into MAX_DENOMINATOR.

Keep bit-size accumulation in log space for reporting, but do not use a saturated sentinel as a probability weight.

Promising alternatives

  • Store a hybrid weight: exact u128 while small, plus logarithm and normalized mantissa after overflow. This avoids a big-integer dependency but is substantially harder to make exact and test.
  • Build discriminant weights directly from worst-case bit costs using log-sum-exp normalization. This preserves minimax ratios approximately and scales well, but the README must stop describing them as exact cardinalities.
  • Reject automatically weighted enums once any payload weight saturates and require explicit manual weights. This is honest and easy, but poor ergonomics for ordinary messages over sixteen bytes.

Acceptance criteria

  • Automatic weighting preserves meaningful ratios for payloads above 128 bits.
  • An enum containing 16-byte and 32-byte uniform payloads has equal worst-case total costs within the documented rescaling tolerance.
  • No saturated sentinel is silently interpreted as an exact cardinality.
High

4. Automatic Option<Vec<T>> weighting defeats the stated sequence policy

Sequences deliberately use a uniform length prefix so short values remain cheap. An enclosing Option, however, weights Some using the vector's full cardinality, which is dominated by the maximum length. Consequently, None becomes almost as expensive as the maximum payload.

For Option<Vec<bool>> with max_len = 64, observed sizes were eight bytes for None, one byte for Some([]), and nine bytes for a full vector. There is no override for Option's automatic weighting.

Evidence: fixed {None: 1, Some: W(T)} policy in src/impls.rs:12–23; vector cardinality in src/seq.rs:113–141.

Recommended solution

Make sum-type discriminant policy explicit and compositional. Introduce a configuration wrapper such as OptionModel<C> with selectable policies:

  • Uniform: cheap and unsurprising presence bit; best default for optional variable-length data.
  • Cardinality weighted: current minimax behavior for uniform fixed-size payloads.
  • Prior weighted: caller-supplied expected-frequency weights.

The derive can select cardinality weighting automatically only when the payload reports uniform per-value cost; otherwise it should default to uniform or require an explicit choice.

Promising alternatives

  • Always use a uniform discriminant for Option. This is simple and unsurprising but gives up the demonstrated two-bit optimal encoding for Option<VehicleClass>.
  • Add only a manual override attribute for option fields, such as #[encode(option(none_weight = 1, some_weight = 1), ...)]. Smaller change, but automatic behavior remains context-sensitive.
  • Weight variants using their encoded-cost distribution instead of cardinality. This is more principled but needs a richer model than the current scalar Weight.

Acceptance criteria

  • Consumers can make None cheap without replacing Option with a custom enum.
  • The chosen default for variable-length payloads is documented with byte-level examples.
  • Size reports expose the None/Some breakdown instead of presenting Option as an opaque leaf.
Medium

5. Untrusted decoding can consume attacker-selected memory and CPU up to max_len

A decoded sequence length is passed directly to Vec::with_capacity, followed by a loop of that length. SeqModel permits u32::MAX, and StringModel accepts that bound. A short malicious stream can therefore request billions of elements or iterations when an application uses a permissive schema.

Evidence: public unrestricted SeqModel fields at src/seq.rs:98–104; allocation at src/seq.rs:225–228; StringModel::new accepts every length fitting in u32.

Recommended solution

Add an explicit decode budget independent of the schema:

  • Maximum elements, maximum allocation bytes, and optionally maximum nesting/work.
  • Use try_reserve and return a typed DecodeError::ResourceLimit or Allocation.
  • Treat max_len as a wire-domain limit and the decode budget as an operational security limit.

Promising alternatives

  • Impose a conservative library-wide maximum. Easy, but arbitrary and inappropriate for some users.
  • Provide iterator/streaming decoding so callers need not materialize the entire sequence. Best for large data, but a much broader API.
  • Document that callers must choose safe max_len values. Necessary regardless, but insufficient for reusable schemas in different environments.

Acceptance criteria

  • No decoded length can cause an infallible large allocation.
  • Nested sequences are constrained by a total budget, not only independent per-field maxima.
  • Security documentation identifies sequence bounds as part of the trust boundary.
Medium

6. Consumers are given no wire compatibility or schema-evolution contract

The format is schema-dependent and non-self-describing. Reordering fields, changing bounds or precision, reordering enum variants, adding a variant, changing weights, or changing a config expression changes the interpretation of bytes. Because correct-length wrong-schema data can decode successfully, this is also an integrity concern.

Recommended solution

Publish a dedicated wire compatibility section that states:

  • Whether wire compatibility is promised across Minnow versions.
  • Which Rust/schema changes are wire-breaking.
  • That both peers must use identical model configuration and variant/field order.
  • How applications should carry schema and protocol version identifiers.

Add an optional deterministic schema fingerprint derived from type shape, model parameters, ordering, and codec version. Include it in the recommended framed format.

Promising alternatives

  • Explicitly declare all 0.x wire formats unstable and require application-owned versioning. This is acceptable for 0.1 if stated prominently.
  • Generate a schema descriptor that consumers can persist or negotiate. More discoverable than an opaque fingerprint and useful for tooling.
  • Adopt stable numeric tags for fields and variants. This enables some evolution patterns but costs bits and changes Minnow's core format.

Acceptance criteria

  • A consumer can determine whether a source-code schema edit is wire-compatible without reading macro internals.
  • The recommended onboarding example includes a schema/version framing strategy.
  • Golden byte fixtures detect accidental wire changes in releases that claim stability.
Medium

7. Marketing and package metadata overstate the demonstrated benefits

The package advertises the keyword lossless, but floating-point fields are explicitly quantized lossily. The README says Minnow “reliably beats DCCL” for its target schemas, while the repository contains one formula-based comparison for one schema rather than a measurement against libdccl. A single report occupies seven whole bytes in both schemes despite Minnow's lower fractional bit count.

The README also begins with a strong guarantee that corrupt and truncated input is always rejected, then correctly concedes later that plausible corrupt input can decode successfully.

Recommended solution

  • Replace lossless with a term such as quantization, telemetry, or compact-binary.
  • Describe float support as schema-declared lossy quantization in the opening section, not only deep in the README.
  • State the DCCL result narrowly: “In the included navigation schema, the documented DCCL formula gives 68 bytes for ten reports versus 65 measured Minnow bytes.”
  • Move the raw-format integrity warning adjacent to the first encode/decode example.

Promising alternatives

  • Reserve “lossless” only for integer/string/enum schemas and qualify it explicitly. Package-level keywords cannot express that nuance well, so removal is preferable.
  • Add real cross-library benchmarks over several DCCL-style schemas. This could justify broader language later.

Acceptance criteria

  • No introductory claim conflicts with a later limitations section.
  • Every comparative performance claim names the measured or calculated scenario.
  • Package metadata accurately describes lossy float support.
Medium/low

8. The stable public surface exposes more codec machinery than most consumers need

EncodeVisitor, DecodeVisitor, OneShot, WeightedModel, precision constants, and bitstream bounds form a second low-level API alongside derive-based encoding. It contains easy foot-guns such as OneShot<0>, out-of-range symbols guarded only by debug assertions, and calling flush twice even though the documentation says consumed-state panics cannot happen through the public API.

The derive crate is also unconditional, so users who only want manual models still compile the full procedural macro and darling dependency stack.

Recommended solution

Define two deliberate API tiers:

  1. A small default surface containing the derive, high-level encode/decode methods, built-in model constructors, errors, and reports.
  2. An advanced module or feature containing visitors and raw arithmetic models, with explicit invariants and fallible constructors.

Make the derive an enabled-by-default Cargo feature so minimal/manual users can opt out.

Promising alternatives

  • Keep the exports but mark the low-level API as unstable and exempt from semver guarantees during 0.x.
  • Replace OneShot<N> with a constructor-validated runtime model. This loses const-generic convenience but prevents N = 0.
  • Make visitor state transitions return typed errors rather than panic. This is useful even if the types remain advanced/public.

Acceptance criteria

  • The primary rustdoc landing page presents only the common consumer journey first.
  • Safe public APIs do not panic on invalid call order or invalid model parameters.
  • default-features = false can avoid compiling the derive stack if the feature split is adopted.
Low

9. DecodeError::Length gives misleading information for short input

The variant stores only a maximum and formats every mismatch as “schema requires at most N.” For an empty or too-short input, that message describes a condition the input already satisfies and omits the actual minimum.

Evidence: src/error.rs:26–49; the implementation computes a lower bound but discards it at src/encodeable_custom.rs:144–149.

Recommended solution

Change the variant to Length { min, max, actual } and render either an exact requirement or a range. For example: “input is 0 bytes; this schema accepts 6..=7 bytes.”

Promising alternatives

  • Split it into TooShort and TooLong. This is convenient for matching but expands a non-exhaustive public enum.
  • Store a RangeInclusive<usize>. Compact, though named fields are somewhat clearer in diagnostics and serialization.

Acceptance criteria

  • Error text accurately explains both undersized and oversized input.
  • Callers can inspect the complete accepted length range.

Architecture and code-quality assessment

Strong delegation

Arithmetic coding and bit-level I/O use established crates rather than hand-rolled implementations.

Clear source layout

Leaf models, sequence/string handling, errors, reporting, visitors, and weighting each have focused modules.

Good derive structure

The parse/process/write pipeline is coherent, and shared product-field generation prevents struct/variant drift.

Appropriate error separation

Encoding, decoding, and invalid model construction have distinct types with useful non-exhaustive variants.

Strong baseline hygiene

unsafe is forbidden, documentation is linted, and the source is readable despite extensive mathematical commentary.

Useful reporting

The size-report tree is a valuable consumer feature and generally provides a conservative byte upper bound.

Complexity worth reducing

  • Duplicated model validation: float/integer validation is manually mirrored in the runtime and proc-macro crates. A small shared non-proc-macro core crate or shared model specification would reduce drift.
  • Saturating cardinality algebra: the hand-rolled Weight representation is elegant for reports but unsuitable as an exact probability source once overflow occurs. Use a solved exact or log-domain representation.
  • Repeated theoretical claims: the same semiring/minimax explanation appears across README and several modules. Keep one authoritative explanation and let API docs focus on contracts, edge cases, and examples.
  • Configuration ownership: EncodeableCustom consumes configs by value, forcing Clone throughout arrays and sequences. Borrowed configuration would be cheaper and would support non-clone custom models.

Testing and delivery assessment

The suite covers structs, tuple/struct/unit variants, arrays, generics, custom models, compile failures, malformed input, sequence limits, and size laws. CI covers stable and nightly Rust, Linux/macOS/Windows, MSRV, formatting, rustdoc, linting, and coverage.

The main blind spots are environmental and property-based:

  • Adversarial sequence tests assert only that decoding does not panic; they do not assert that truncation returns Err.
  • Float tests use grid-aligned endpoints and therefore miss the valid-model panic.
  • Size-law fixtures stay below or do not compare across cardinality saturation in unequal enum variants.
  • Deterministic random-input loops are useful smoke tests but are not a substitute for property tests and persistent fuzz corpora.

Recommended additions

  • proptest coverage for model constructor invariants and encode/decode fixed points.
  • A cargo-fuzz target for raw and framed decoding, including nested bounded sequences.
  • Golden wire fixtures once a compatibility policy is selected.
  • Regression tests for every concrete reproduction in this report.
